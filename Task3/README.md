# 1. ТЕХНОЛОГИЧЕСКИЙ РАДАР «БУДУЩЕЕ 2.0»

Радар разделён на зоны:

* Adopt (внедряем сразу)
* Trial (тестируем в отдельных доменах)
* Assess (оцениваем и смотрим)
* Hold (оставляем, но не развиваем)

И на кольца:

* Инфраструктура
* Данные
* Аналитика и ИИ
* Интеграции
* Приложения / UX

## ADOPT (внедряем сразу)

### 1. Lakehouse (Iceberg)

Поддерживает:

* формирование доменных витрин
* масштабирование под сотни ТБ

Причина: уходит зависимость от SQL Server 2008, появляется параллельность и нормальная работа с потоками.

### 2. API Gateway (Kong + OIDC)

Поддерживает:
* безопасность для данных внутри контура
* подключение партнёров
* единая точка входа

Причина: единый контроль прав и трафика.

### 3. Data Mesh 

Поддерживает:

* независимое развитие клиники, финтеха, ИИ
* подключение партнёров (фарма → клинические исследования, производители оборудования → телеметрия)

Причина: каждый домен владеет своими наборами данных, исчезает «бутылочное горлышко» DWH.

### 4. Kafka (Event Bus)

Поддерживает:

* обмен событиями между доменами
* подключение новых сервисов без изменения DWH
* real-time обновления витрин

Причина: ключевой транспорт между доменами.

### 5. Data Orchestrator (Airflow)

Поддерживает:

* запуск витрин из портала
* наблюдаемость, SLA
* надёжность пайплайнов

Причина: портал не должен управлять Spark напрямую.

### 6. Облачная инфраструктура (Kubernetes + Object Storage + Managed DB)

Поддерживает:

* масштабирование под рост компании
* быстрый time-to-market
* резервирование и надёжность

Причина: уход от устаревшего железа, экономия.

## TRIAL (пилоты)

### 7. Feature Store (Feast)

Бизнес-сценарии:

* поддержка ИИ (скоринг, прогнозирование)
* совместное использование фич мед + фин

---

### 8. Federated Governance (Data Catalog)

Бизнес-сценарии:

* консистентные показатели для головного офиса
* единая терминология
* понятная lineage для аудита финтеха


### 9. AutoML / ML Observability (Evidently / Arize)

Бизнес-сценарии:

* стабильные ИИ-модели для медицины
* выявление деградации качества

---

## ASSESS (оценка, возможно позже)

### 10. Apache Doris (OLAP)

Поддерживает:

* быстрая отчётность
* формирование доменных витрин для BI
* отдельный compute для аналитики и построения отчетов

Причина: Слой оперативных данных для аналитики, отчетов, дашбордов.

### 11. Streaming ETL (Flink / Spark Structured Streaming)

Полезно для real-time финтех-витрин и клинических событий.
Но пока не обязательное.

### 12. Self-Service SQL Editor ( Grafana Data Explorer)

Портал самообслуживания уже есть, но можно расширить функциональность.

## HOLD (оставляем, но не развиваем)

### 13. SQL Server 2008 DWH

Только как источник исторических данных.
Никакой новой логики, перенос постепенно.

---

### 14. Apache Camel шина

Только как временный слой.
Всё новое — Kafka.

# 2. ГОДОВОЙ РОАДМАП (на 12 месяцев)

Деление: квартал → шаги → результаты → команды → ресурсы.

# Q1: Фундамент платформы

### Шаги:

* Развёртывание облачной инфраструктуры (Kubernetes, Object Storage).
* Развёртывание Lakehouse: Bronze/Silver/Gold.
* Внедрение Kafka как внутреннего event bus.
* Поднятие API Gateway + OIDC.
* Разработка схем доменного разделения данных (Data Mesh blueprint).

### Ожидаемые результаты:

* готов фундамент для доменных витрин;
* домены получают собственные зоны данных;
* новые сервисы больше не пишут в DWH.

### Команды:

* инфраструктура, data platform, безопасность.

### Ресурсы:

* облачные бюджеты, лицензии (если нужны).

---

# Q2: Витрины и оркестрация

### Шаги:

* Внедрение Data Orchestrator (Airflow).
* Формирование первых доменных DDP: медицина и финтех.
* Подключение CDC при необходимости.
* Базовая версия портала: запуск пайплайнов, статусы.
* BI подключается к Vitirna Gold, а не к DWH.

### Ожидаемые результаты:

* первые витрины собираются автоматически;
* финтех перестаёт зависеть от DWH;
* отчёты становятся быстрее в 5–10 раз.

### Команды:

* data engineers, архитектура доменов, BI.

---

# Q3: Интеграция ИИ и партнёров

### Шаги:

* Внедрение Feature Store.
* Подключение ИИ-компании к обезличенным данным.
* Подключение производителей мед.оборудования через API Gateway.
* Подключение финтех-партнёров (страховые компании).
* Полный перевод очередной части логики с SQL DWH в домены.

### Ожидаемые результаты:

* ИИ получает данные легально и прозрачно;
* партнёры интегрируются без «запила Camel»;
* появляются первые модели, влияющие на выручку.

### Команды:

* AI/ML, data platform, security, интеграции.

---

# Q4: Завершение трансформации

### Шаги:

* Продвинутая версия портала: self-service отчёты, витрины по кнопке.
* Перенос отчётности головного офиса на новые DDP.
* Минимизация использования Legacy DWH до уровня read-only.
* Governance: каталог данных, lineage, SLA.
* Наблюдаемость ML-моделей (drift detection).

### Ожидаемые результаты:

* компания полностью перешла на доменную архитектуру;
* time-to-insight снижён с часов до минут;
* DWH больше не является центром сложности;
* каждый домен развивается сам.

### Команды:

* все ИТ-направления, архитектура, бизнес-аналитики.


# 3. ОБОСНОВАНИЕ ПЛАНА (понятным языком)

### Почему нужен Lakehouse?

Потому что текущий DWH медленный и негибкий. Большая связнаять внутри одного DWH. Деградация аналитики
Lakehouse даёт параллельность и скорость → отчёты формируются в минуты.

### Зачем Data Mesh / домены?

Чтобы каждый бизнес (клиники, финтех, ИИ, партнёры) развивался независимо.
Без очередей на изменения в DWH.

### Зачем Kafka?

Новые сервисы подключаются без изменения DWH.
Вместо «ETL из слоёв» — обмен событиями.

### Зачем портал самообслуживания?

Чтобы бизнес мог сам запускать витрины и отчёты.
Без ожидания разработчиков или ночных ETL.

### Зачем оркестратор?

Чтобы процессы были надёжными, прозрачно логировались и контролировались.
Иначе портал превратится в костыль.

### Зачем уход от SQL Server 2008?

Потому что на нём держится бизнес-логика, и любое изменение стоит месяцы.
Мы убираем логическую нагрузку на домены.

### Зачем governance?

Чтобы при подключении фарм и электроники у всех были одинаковые правила:
права, маскирование, lineage, аудит, контракты и качество данных.
