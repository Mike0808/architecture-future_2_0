# Justification: Обоснование инфраструктуры и Terraform-конфигурации

## 1. Логика архитектуры

Инфраструктура построена вокруг базовых IaaS-компонентов:

- **yandex_vpc_network** с отдельными публичной и приватной подсетями.
- **Public Subnet** — зона для bastion-хоста, имеющего публичный IP для администрирования.
- **Private Subnet** — зона для data-VM, на которой размещаются сервисы работы с данными (Lakehouse/ETL/оркестратор и т. д.).
- **Internet Gateway** — даёт выход в интернет для публичной подсети.
- **NAT Gateway** — обеспечивает исходящий доступ в интернет из приватной подсети (обновления, репозитории) без прямой доступности снаружи.
- **Security Groups** — реализуют сетевую сегментацию на уровне L4.

Такое разделение позволяет:

- изолировать критичные сервисы (данные, ИИ, ETL) в приватной подсети;
- контролировать доступ к ним через bastion и Security Groups;
- упростить выполнение требований безопасности и регуляторов (особенно для мед- и финтех-сервисов).

## 2. Виртуальные машины и диски

Выбраны два типа инстансов:

- **Bastion VM (t3.micro)**  
  Минимальный тип, достаточный для SSH-доступа и туннелирования. Не несёт бизнес-нагрузки, только админ-доступ. Экономит бюджет.

- **Data VM (t3.large)**  
  Машина для сервисов данных (Spark-наборы, оркестратор, ETL-агенты, вспомогательные сервисы). Тип можно масштабировать в зависимости от нагрузки.

Отдельный **EBS-диск** для data-VM:

- упрощает перенос и масштабирование;
- разделяет системный и прикладной диски;
- позволяет настраивать производительность и размер отдельно от типа инстанса.

## 3. Сетевые настройки и NAT

Использование NAT Gateway для приватной подсети позволяет:

- обеспечить VM-доступ в интернет (репозитории пакетов, Docker-образы, обновления);
- при этом не открывать входящие соединения в приватную подсеть;
- соответствовать типичной best practice для продакшн-инфраструктуры (особенно для данных с регуляторными ограничениями).

Public Subnet получает прямой доступ к интернету через Internet Gateway, но туда выносится только bastion.

## 4. Что управляется Terraform, а что вручную

**Terraform управляет:**

- yandex_vpc_network, подсетями, маршрутизацией;
- yandex_vpc_gateway;
- Security Groups;
- yandex_compute_instance (bastion и data-VM);
- yandex_compute_disk и его подключением.

**Вручную настраиваются:**

- Yandex-аккаунт;
- IAM-пользователь/роль для Terraform (минимальные права);
- SSH key pair, имя которого передается в переменной `ssh_key_name`.

Такое разделение логично, потому что:

- создание аккаунта и базового IAM часто относится к зоне ответственности секьюрити/платформенной команды;
- Terraform удобнее использовать в уже существующем аккаунте с подготовленной ролью.

## 5. Почему декларативный подход (Terraform)

Terraform описывает желаемое состояние инфраструктуры декларативно. Это даёт:

- **Воспроизводимость**: любая среда (dev, test, prod) может быть поднята по одной и той же конфигурации.
- **Прозрачность изменений**: `terraform plan` показывает, что именно будет создано/изменено/удалено.
- **Контроль версий**: конфигурация хранится в Git, изменения проходят через code review и pull request.
- **Audit-trail**: всегда понятно, кто и когда изменил инфраструктуру, по истории коммитов.

Для компании с мед- и финтех-направлениями это критично, так как:

- инфраструктура проверяется аудиторами и регуляторами;
- необходимо контролировать права доступа и конфигурации;
- повторяемые среды снижают риск ошибок при релизах.

## 6. Масштабируемость и развитие

Подход Infrastructure as Code упрощает масштабирование:

- можно изменить переменные (размер дисков, тип инстанса, CIDR) и пересоздать инфраструктуру;
- можно легко добавить новые подсети, домены, сервисы в тот же Terraform-проект;
- упрощается подключение новых бизнес-направлений (например, отдельный yandex_vpc_network/подсеть под фарм-партнёров).

В контексте трансформации «Будущего 2.0» это значит:

- быстрое разворачивание новых окружений под домены (клиники, финтех, ИИ, партнёры);
- снижение зависимости от ручных настроек администраторов;
- прозрачная и повторяемая инфраструктура, соответствующая принципам Data Mesh и доменной архитектуры.

## 7. Связь с бизнес-целями

- **Скорость принятия решений**: инфраструктура для анализа и отчётности может быть поднята и масштабирована за часы, а не недели.
- **Качество сервиса**: приватные подсети и SG снижают риск инцидентов безопасности.
- **Снижение затрат**: использование облачной IaaS и автоматизации уменьшает ручные операции и риски ошибок.
- **Масштабирование**: новые домены и партнёры подключаются через повторяемые Terraform-конфигурации, а не через ручной «зоопарк» настроек.
